MPICH
└── CH4
     ├── SHM               → 同节点共享内存

当前自编 MPICH 4.2.2 使用 `CH4:OFI` 和内置 libfabric：

- 当前正式配置显式设置 `FI_PROVIDER=tcp`；已通过单节点 2-rank Comb smoke test，可以运行。
- 默认 `verbs` 会选择 `mlx5_0`，但创建 UD QP 时返回 `Operation not permitted`，当前不能运行。
- 同一计算节点上，Intel MPI 自带 libfabric 已成功识别 `mlx5_0` 的 verbs/RC/RXM endpoint，说明硬件和作业权限支持 RDMA；故障来自当前 MPICH 内置 libfabric，而不是集群禁止使用 verbs。
- 因此只是当前这份 MPICH 构建暂时使用 TCP，并非 MPICH 本身只能用 TCP。verbs 修复暂时搁置，后续如需 RDMA，再使用兼容 CM4 的外部/新版 libfabric 重新构建并验证。
- 修复前的 MPICH TCP 结果可与 OpenMPI TCP 对照，不能直接与 Intel MPI verbs/RDMA 结果视为同一种网络路径。

## Comb 网格、halo 与 self-message 备忘

- Comb 是结构网格 halo-exchange benchmark，不求解浅水方程等 PDE。网格值是用于填充、打包和校验通信的测试值；`mid-comm` 是可选的合成浮点计算，用于模拟计算-通信重叠。
- `small_msg` 配置：全局网格 `32x32x32`，`divide=2x1x1`，`ghost=1x1x1`，`periodic=1x1x1`，每个 rank 的内部块为 `16x32x32`，数据类型为 `double`（8 B）。
- Y/Z 未切分但为周期边界，所以 Y/Z 的逻辑邻居仍是本 rank。Comb 对它们仍按完整 MPI 路径处理，而不是直接特判为 memcpy：`pack -> MPI_Irecv/Isend(self) -> wait -> unpack`。
- 发给自己的消息为 `2112` items = `16896` B：四个 Y/Z 面块各 `16x32x1=512` items，四个 YZ edge 条带各 `16x1x1=16` items。面块只覆盖单方向边界；edge 单独处理，避免同一 ghost cell 被两个面重复打包/写入。
- 发给另一 rank 的消息为 `2312` items = `18496` B：包含 X 面、XY/XZ edge 和 XYZ corner 数据。
- `-print_message_sizes -print_packing_sizes` 只打印静态通信/打包计划，不实际通信、不参与计时。该版本的总行标签有错位；第一列才是实际 partner rank。
- 当前 `wait_recv=wait_all`：`wait-recv` 计时包含所有 recv（self 和 remote）的 `MPI_Waitall`、随后所有接收 buffer 的 unpack/deallocate；日志没有 self/remote 的单独拆分。
- Mock 复用相同消息布局并包含 buffer 的 unpack 等内存工作，但不执行任何 MPI。因此 `MPI wait-recv - Mock wait-recv` 仍包含 self-message 的 MPI 请求/匹配成本，不能视为纯跨 rank 通信时间。

## overlap 图中蓝柱与红柱的计算

图中每个 case 都比较同一通信后端、同一 mesh/buffer 策略下的一对结果：`no_midcomm`（不插入计算）和 `midcomm`（在 `post-send` 后、`wait-recv` 前插入合成计算）。MPI 和 mock 面板使用相同公式，但 backend 不同。两根柱都不是直接画 `MPI - Mock`。

### 蓝柱：Compute overlap rate

蓝柱只观察 `wait-recv` 这个阶段缩短了多少：

```text
blue = (wait_recv_no_mid_avg - wait_recv_mid_avg) / mid_comm_avg * 100%
```

- `wait_recv_no_mid_avg`：`no_midcomm` CSV 中 `wait-recv` 的每次平均时间。
- `wait_recv_mid_avg`：`midcomm` CSV 中 `wait-recv` 的每次平均时间。
- `mid_comm_avg`：`midcomm` CSV 中合成计算 `mid-comm` 的每次平均时间。
- 三者都是相同 rank/cycle 样本集合的每次平均值，所以公式中不乘 cycle 数或 rank 数。

蓝柱为正表示：插入计算后，`wait-recv` 平均变短；这个差值可被解释为在计算期间隐藏的等待时间。蓝柱为负表示：有计算时 `wait-recv` 反而更长，可能来自额外开销、调度变化或测量噪声。图中蓝色 `overlap ... us/ms` 标注则将每次差值换算为一个关键路径 rank 的全部 cycle 总量：

```text
wait_recv_overlap_total = (wait_recv_no_mid_avg - wait_recv_mid_avg)
                          * mid_comm_num / ranks
```

例如 2 ranks、50 cycles 时，`mid_comm_num=100`，因此总量为每次差值乘 `100 / 2 = 50`。

### 红柱：Overall overlap gain

红柱看的是整个 benchmark 的关键路径，而不仅是 `wait-recv`。先构造“计算和通信完全串行、没有任何隐藏”的基线：

```text
mid_compute_total = mid_comm_avg * mid_comm_num / ranks
serial_total = bench_no_mid_max + mid_compute_total
red = (serial_total - bench_mid_max) / serial_total * 100%
```

- `bench_no_mid_max`：`no_midcomm` 的 `bench-comm` 最大值，即最慢 rank 完成全部 cycles 的总时间。
- `bench_mid_max`：`midcomm` 的 `bench-comm` 最大值，即最慢 rank 在插入计算后完成全部 cycles 的总时间。
- `mid_compute_total`：一个 rank 在所有 cycles 中注入的计算总时间。
- `bench-comm` 在 CSV 中通常 `number=ranks`，因为它是每个 rank 一次的整段计时；它本身已覆盖全部 cycles。因此上式必须把 `mid-comm` 从 rank x cycle 的平均样本换算为单个 rank 的全部 cycle 总时间，才能与 `bench-comm` 同量纲。

红柱为正表示实际 `midcomm` 总关键路径短于串行基线，图中红色 `saved ... us/ms` 是 `serial_total - bench_mid_max` 的绝对时间。红柱为负表示实际总时间比串行基线更长。红柱还会包含 `post-send`、打包/解包、OpenMP 调度等变化，因此它不必等于蓝柱。

### mock 面板如何判读

mock 不执行真实 MPI 传输，不存在可由计算隐藏的远端通信等待。因此理想情况下：

```text
blue_mock ~= 0%
red_mock  ~= 0%
```

- mock 蓝柱偏离 0：是无真实通信时 `wait-recv` 基线的波动或框架效应，不是通信 overlap。
- mock 红柱偏离 0：是总关键路径计时、线程调度、cache 或资源竞争造成的偏差，不是“mock 获得了重叠”。
- 只有 MPI 柱在多次重复中持续显著超过同条件 mock 的波动范围，才可以谨慎归因于真实 MPI 通信与 mid-comm 的重叠。

#### 本点负差值的原因记录

负值不是网络耗时小于零，而是当前 Mock 不能作为“仅去掉网络、其余完全
相同”的严格对照。以 Intel MPI Case 01 `omp/omp-omp` 为例，MPI 与 Mock
的 `wait-recv` 分别为 402.552 和 454.028 $\mu s$，因此相减得到
$-51.476\ \mu s$。但异常并不局限于这一阶段：Mock 的 `post-send` 为
465.227 $\mu s$，也明显高于 MPI 的 260.233 $\mu s$；六个阶段
`pre-comm` 至 `post-comm` 的每 cycle 合计分别约为 1,211.3 和
883.4 $\mu s$，即 Mock 整条路径反而慢约 327.9 $\mu s$。

源码中的 MPI 与 Mock 使用相同的外层 cycle 和 pack/unpack 流程，但存在
两个关键差异：

- Mock 的 `Irecv` 只把整数 request 标为待完成，不向接收 buffer 写入数据；
     随后的 `wait-recv` 仍读取该 buffer 并执行 unpack、deallocate 和同步。
     MPI 的接收 buffer 则在 unpack 前已由真实传输写入，因此两者的内存页和
     cache 状态不等价。
- 同一进程固定先完整运行 Mock，再运行 MPI，而不是随机交错或独立配对。
     后运行的 MPI 可能受益于 allocator、页表和 cache 已预热；这与本次 Mock
     的 `post-send`、`wait-send` 也系统性更慢相符。

“未写入的 Mock 接收 buffer 在 unpack 时发生首次触页/cache miss”是当前
最合理的机制解释，但尚需通过预填充 Mock recv buffer、交换 MPI/Mock
运行顺序或分别启动独立进程来验证。现阶段应把负值标记为 Mock 基线失效，
保留 MPI 与 Mock 原始值，不取绝对值、不截断为零，也不用于设定
`compute_target_us`。

## cm4_std：2n2r 与 4n4r Job Bundle 消息大小扫描

本节是新增的 `cm4_std` 实验配置，不修改、不替代上面的 `cm4_inter`
实验记录。生成目录分别为 `generated/cm4_std/<mpi>/2n2r_c24/` 和
`generated/cm4_std/<mpi>/4n4r_c24/`；两种 topology 使用各自的 vars，
不再共用同一套 std grid。

统一设置：

```text
cluster   = cm4
partition = cm4_std
qos       = cm4_std
topology  = 4n4r_c24
nodes     = 4
ranks     = 4（每节点 1 rank）
divide    = 2_2_1
periodic  = 1_1_1
ghost     = 1_1_1
cycles    = 100
runs      = 3（本次实际目录为 run_001、run_002、run_003）
```

`4n4r_c24` 有 4 个 MPI ranks，因此 `divide` 三维乘积必须为 4；这里使用
`2_2_1`。`2_1_1` 是上面 `cm4_inter/2n2r_c24` 的配置，不能直接用于
4-rank bundle。

每种 MPI 的顶层 `run.sh` 是唯一包含 `#SBATCH` 的脚本。它在一次资源分配
内串行执行：

$$
19\ \text{payloads}\times 2\ \text{compute modes}\times 3\ \text{runs}
=114\ \text{children/MPI}.
$$

子脚本不包含 `#SBATCH`，只在顶层 allocation 中启动 `srun/mpirun` job
step。四种 MPI 共 456 个子实验。
